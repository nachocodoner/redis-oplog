# Redis Oplog reactive behavior audit and implementation roadmap

**Decision as of 23 November 2026.** Keep the 3.0.1 runtime and its pinned client as the reference. Six package runs each passed 21 server and 158 browser cases, with three server cases pending. A separate two-process test propagated a projected insert, update and removal to a browser. A controlled write between the initial Mongo read and Redis subscription was missed. During recovery, a different race restored a document the browser had already removed after receiving its live delete. A matched upsert that changes its selector field and a skip-only query also left live observers stale. With the bridge, a sorted winner could remain wrong after an external update and a direct observer could miss a string ID. Protect the working behavior, then fix those cases before changing the driver or tuning fan-out. Redis 8.12.0 already passes the existing suite on Meteor 3.1.2, 3.2 and 3.6.1 with the shipped JavaScript client. The server upgrade work is principally compatibility testing and operational documentation. [Redis 8.12 GA](https://github.com/redis/redis/releases/tag/8.12.0)

**Local branch status.** The local branch `cross-instance-tests` fixes the initial snapshot handoff (R1), matched upserts leaving their selector (R2), skip-only window membership (R3), overlapping delivery during recovery (R6), and the interval before Redis restores subscriptions (R7). The default two-process browser run exercises these cases. On Meteor 3.6.1 the branch also fixes ordinary sorted queries falling back to polling (R8). The branch now also fixes R9 through R11. All 27 upstream observer cases pass in both lanes on Meteor 3.6.1, compared with nine server failures on published 3.0.1. The package and two-process suites also pass on standalone Redis 8.12.0 with node-redis 3.1.2. The architecture inventory describes the audited 3.0.1 revision. ## From database write to client result

Redis Oplog addresses the cost of every Meteor server tailing a database-wide oplog to work out which live queries changed. The application already knows many of the IDs it writes. Publishing targeted Redis notifications lets each process listen to relevant collections, documents or application-defined groups while MongoDB remains the source of persistent data. This is particularly attractive for disjoint chat rooms or tenants and for ephemeral events that do not warrant a database write. The benefit depends on how well the routes partition the workload and on the cost of pre-reads, re-fetches and another service. [How it works](how_it_works.md) · [Fine tuning](finetuning.md)

1. **Installation and ownership.** The server entry installs a collection-name shim and initializes once from `REDIS_OPLOG_SETTINGS` (first choice), `Meteor.settings.redisOplog` or explicit `RedisOplog.init`. Initialization deep-merges settings, replaces collection mutators and validated mutation paths, and assigns `MongoInternals.Connection.prototype._observeChanges`. The client retains Meteor's DDP and Minimongo. Collection creation order and packages that also wrap prototypes matter. The README calls for early package ordering, recommends disable-oplog and excludes insecure. On modern Meteor, disable-oplog alone does not select the observation driver. This package actually replaces the selection function. [Entry](../redis-oplog.js) · [Initialization](../lib/init.js) · [Collection wrappers](../lib/mongo/extendMongoCollection.js) · [Observe override](../lib/mongo/extendObserveChanges.js)
2. **Starting an observer.** A publication returning a cursor triggers Meteor's observe machinery. The replacement keys a multiplexer on EJSON of the cursor description and ordered flag, shares equivalent handles within a connection, and delegates tailable cursors. A compilable unordered selector/sort and supported projection can use Redis. Ordered callbacks, an explicit disable flag, unsupported compilation and geo/where cases take the package's copied polling path. Excluding _id from an observed projection throws. The Redis driver creates a Mongo cursor, applies the per-collection cursor hook, fetches initial documents, adds them to a per-query ID map and signals multiplexer readiness. Only then does it construct a RedisSubscriber. Its attach and underlying SUBSCRIBE are queued. A matching second handle receives the cached adds. [Selection](../lib/mongo/observeChanges.js) · [Driver.init](../lib/mongo/RedisOplogObserveDriver.js) · [ObservableCollection](../lib/cache/ObservableCollection.js) · [Multiplexer](../lib/mongo/ObserveMultiplex.js)
3. **Writing.** MongoDB owns persistent state, write selection and write results. Redis Oplog wraps server insert/update/remove and Async equivalents. Meteor upsert reaches the update path. Mutation defaults, method context, invocation options and the collection hook determine routing and optimism. Ordinary updates pre-read IDs (one unless multi), restrict the write to that set, then dispatch a message per candidate. Remove pre-reads too. Upsert has a separate insertedId/matched branch. A pre-read and a write are separate database operations. Neither forms a transaction with publishing. Raw driver calls, bulkWrite, database jobs and other languages bypass these wrappers. [Mutator](../lib/mongo/Mutator.js) · [Configuration resolution](../lib/mongo/lib/getMutationConfig.js)
4. **Publishing.** A persistent message carries operation `e` (i/u/r), document `d` with at least _id, update field hints `f`, and source `u` when applicable. EJSON preserves Meteor types. Normal dispatch covers the configured collection/custom/namespace channels plus a dedicated ID channel. Optimistic writes first process applicable local observers and tag the origin with its process UID. The ordinary Redis send is deferred. A successful write or returned Promise does not acknowledge any remote observer. Outside a method optimistic processing defaults off unless explicitly forced. `pushToRedis:false` takes the original write path. `externalRedisPublisher:true` suppresses ordinary outbound publishing and keeps the optimistic local path when requested. [Dispatch](../lib/mongo/lib/dispatchers.js) · [Protocol](../lib/constants.js) · [Optimistic UI](optimistic_ui.md)
5. **Receiving.** There is a shared publisher socket and a separate subscribed socket per process. PubSubManager decodes EJSON. RedisSubscriptionManager maps channel to interested query drivers, serializes received work, and ignores its own optimistic echo. For ordinary inserts/updates it typically fetches once by ID per channel message using the union of interested fields, including selector dependencies. One broad/exclusion subscriber can require the whole document. With protection disabled it trusts the supplied document. Removes use payload identity. The chosen processor re-matches, diffs or re-queries the window. The multiplexer forwards added/changed/removed, Meteor merges publication views and sends DDP, and client Minimongo applies the changes and invalidates reactive consumers. One raw event can produce zero callbacks or multiple membership changes. [Redis manager](../lib/redis/RedisSubscriptionManager.js) · [Field union](../lib/redis/lib/getFieldsOfInterestFromAll.js) · [Processors](../lib/processors) · [Meteor cursor publication](https://github.com/meteor/meteor/tree/eaf134973529396b660078b705b9fa50a4747fd5/packages/mongo)
6. **Stopping and reconnecting.** Last-handle removal drops the observe key and stops the driver. Detach queues channel removal, final unsubscription and handler deletion. Listener connect triggers a query reload/diff for every registered subscriber entry. Attach, Redis subscribe acknowledgement, reload and delivery have different completion boundaries. Reconnect attempts to repair current persisted membership. Synthetic state has no Mongo history. Fresh processes construct fresh observers and initial snapshots. [Lifecycle](../lib/redis/RedisSubscriber.js) · [Channel manager](../lib/redis/PubSubManager.js) · [Reload](../lib/processors/actions/reload.js)

### Delivery contract

Redis Pub/Sub delivers each publication at most once to a connected recipient on a subscribed channel, in Redis publication order. A disconnected subscriber can miss everything in the gap. Redis database numbers do not isolate channels. Mongo commit order across writers, deferred publish order, the local optimistic path, different channels and different clients do not form a single ordering domain. A read on receipt can already see a newer write or a deleted document. The UID identifies an originating process and suppresses its own echo. It is shared across that process's optimistic events. There is no per-mutation sequence, durable queue, consumer acknowledgement, outbox or replay cursor in Redis Oplog. Duplicate publishes and overlapping routes can repeat work. Some identical state transitions yield an empty diff. No end-to-end exactly-once, every-intermediate-state, bounded-lag or unconditional convergence guarantee follows. A committed write followed by a publisher crash can leave a still-connected peer stale until a relevant later change or refresh. [Redis Pub/Sub semantics and scoping](https://redis.io/docs/latest/develop/pubsub/) · [Dispatchers](../lib/mongo/lib/dispatchers.js) · [Failover documentation](failover.md)

## Three ways to deliver a Mongo change

| Dimension | Redis Oplog alone | Native Meteor 3.6.1 | Change Stream to Redis + Redis Oplog |
|---|---|---|---|
| Detector / writes | Application wrapper or explicit publisher knows which documents it wrote. Raw/external writes need application cooperation. | Mongo commit stream captures supported insert/update/replace/delete from any writer on a watched collection. | A separate service watches a Mongo database, filters operations and supported IDs, translates and publishes them for all connected app servers. Includes raw writes and bulk members with matching events. |
| Routing and sharing | One Redis channel subscription per interested process/channel. Identical observations share a multiplexer. ID and opt-in tenant routing reduce local matches. | One shared watch per Mongo connection and observed collection per process. Every attached query driver receives each collection event. Identical observe descriptions share a multiplexer. | One database watch per bridge, optionally two disjoint collection sets. Redis distributes events through the same Redis Oplog query drivers. Multiple bridges can see the same writes. |
| Maintaining results | Read by ID per interested channel event by default, locally re-match/project and diff. Reconcile limited windows with Mongo reads. Full-image mode trades reads for payload bytes. | Requests updateLookup and pre-image when available. Converts BSON, tests before/after membership using matcher and cache, projects and diffs. Deletes use cache membership. Begins with a Mongo query and may re-query on recovery. | Default ID-only message incurs consumer reads. Optional full images need agreement with the consumer. Field hints and ID encoding differ in consequential cases below. |
| Bootstrap / recovery | Snapshot before subscribe, listener connect reload. No replay for Pub/Sub. | Attaches driver to shared stream before initial snapshot, buffers pending writes, deduplicates overlap and uses eligible causal primary snapshot boundaries. Resumes cursor with in-memory token, handles history loss by reopening and reconciling persisted state. Process restart builds a new snapshot. | Producer can resume from Redis checkpoint. Consumer still has the Redis Oplog snapshot/reconnect boundaries. A producer gap with a healthy Redis connection does not trigger consumer reload. |
| Query boundary | Unordered matchable cursors, dedicated IDs, explicit routing and some limited windows. Own polling fallback. | Requires Mongo 6.0.9+ on the 6.0 line or newer supported versions, replica set or sharded deployment, watch privileges. Ordered, skip/limit, unsupported projections, geo/where and identified divergent selectors/collations fall through the configured order. | Mongo must support database change streams, selected pipeline operators, requested images and driver version. Same observation restrictions as Redis Oplog plus wire/routing constraints. |
| Cost and scaling | Per-write pre-read, publishes per ID/channel, per-receiving-process reads, event queue and projected caches. Hot channels can serialize unrelated queries. | Each process pays a watch/getMore stream per active collection and handles its fan-out. Per-driver conversion/matching, queued changes and cached results consume CPU/RAM. Full images and update lookups cost Mongo/network. Avoids Redis and producer pre-reads. | Concentrates watching in the bridge. Adds Rust queue, optional image lookups, Lua invocations, routing and Redis traffic. Scales consuming app processes independently. Batching may reduce requests while increasing latency. |
| Operations and fit | Application-controlled notifications, synthetic state and custom routing. Possible on standalone Mongo where the Meteor release supports it. Requires Redis availability and consistent writers. | Smallest infrastructure footprint for persistent data on eligible Mongo. Native write fences coordinate DDP with change progress subject to a timeout. | Useful for unmodified external writers plus existing Redis Oplog query/routing or Vent needs. Operate a supervised bridge, appropriately retained Mongo history and optional durable checkpoint keys. |

The historical 3.5 implementation opened `collection.watch([], options)`. The current watch adds the large-event split stage. Neither installs a Mongo predicate per publication. A selective publication can save DDP traffic while the app still receives every watched collection event. In 3.5 the minimum version check was major >= 6. Subsequent releases added non-resumable history recovery (3.5.1), snapshot overlap fixes (3.5.2), and later fragment reassembly/fence holds. Current resync is best effort per driver and logs errors. Fences can time out and temporarily relax read-your-writes. Fresh query results are a realistic comparison oracle across all three systems. All three can collapse or miss intermediate states under the conditions described above. [3.5 implementation](https://github.com/meteor/meteor/blob/3f23e5e402cf9091a4515cb94130b6a0a9ced11e/packages/mongo/shared_change_stream.js) · [Current selection](https://github.com/meteor/meteor/blob/eaf134973529396b660078b705b9fa50a4747fd5/packages/mongo/mongo_connection.js) · [Shared cursor and restart](https://github.com/meteor/meteor/blob/eaf134973529396b660078b705b9fa50a4747fd5/packages/mongo/shared_change_stream.js) · [Snapshot, matcher and fences](https://github.com/meteor/meteor/blob/eaf134973529396b660078b705b9fa50a4747fd5/packages/mongo/changestream_observe_driver.js) · [Driver documentation](https://docs.meteor.com/performance/change-streams-observer-driver)

These approaches can complement one another across services or with an explicitly integrated observation strategy. Installing Redis Oplog 3.0.1 in a native-change-stream application replaces the global observe entry point. A per-query hand-off back to Meteor's driver registry would be a new integration. The supported composition to investigate today is a Mongo change-stream producer with a Redis Oplog consumer.

### Bridge wire and recovery contract

Use `externalRedisPublisher:true` and a literal `globalRedisPrefix` of the Mongo database name followed by a dot. For database shop, collection orders, ID abc, the bridge sends to `shop.orders` and `shop.orders::abc`. With `NAMESPACES=orders.team`, the scalar value red also routes to `shop.team::red::orders`. Arrays contribute elements and objects contribute keys. Arbitrary application channel functions are outside this protocol. String and BSON ObjectId are admitted. Numeric and other IDs and DDL operations are filtered out. ObjectId becomes typed Meteor EJSON in the payload and hex in the channel. Plain special strings require extra escaping on the Meteor side. The default update is shaped like `{"e":"u","d":{"_id":"abc"},"f":[]}`. Both replace and update become u. A delete becomes r. There is no writer UID. Dates, binary, Decimal and several other BSON types have explicit conversions, with remaining unhandled types mapped to null. Verify exact numerical and EJSON literal-object round trips before trusting whole images. [Pipeline](https://github.com/radekmie/changestream-to-redis/blob/bab84905c3871e50f3d65bebc5a8dc65eff9a1ce/src/mongo.rs) · [Type conversion](https://github.com/radekmie/changestream-to-redis/blob/bab84905c3871e50f3d65bebc5a8dc65eff9a1ce/src/ejson.rs) · [Meteor ID encoding](https://github.com/meteor/meteor/blob/3f23e5e402cf9091a4515cb94130b6a0a9ced11e/packages/mongo-id/id.js)

The bridge opens Redis, optionally reads `REDIS_RESUME_TOKEN_KEY`, then opens a database watch, or two for `FULL_DOCUMENT_COLLECTIONS`. A bounded channel (default 1024) feeds batches (default 1). A Redis script publishes the routes and optionally stores per-stream token progress in the same invocation. `startAfter` is per stream. A missing/invalid token starts at the current position. Expired history errors 280/286 on opening are logged and start at the current position. Publication I/O errors can be retried up to the configured count (default zero). Terminal watch/Redis failures require supervision. In particular the watch task uses unwrap and a closed sender can let main finish after draining. Supervise even a clean exit. A lost/evicted key, a code-286 fallback, or a disconnected consumer can all cause different gaps. Only the first two concern producer progress. Multiple streams are polled with biased selection and have independent checkpoints. [Startup and queue](https://github.com/radekmie/changestream-to-redis/blob/bab84905c3871e50f3d65bebc5a8dc65eff9a1ce/src/main.rs) · [Lua and retries](https://github.com/radekmie/changestream-to-redis/blob/bab84905c3871e50f3d65bebc5a8dc65eff9a1ce/src/redis.rs) · [Tokens](https://github.com/radekmie/changestream-to-redis/blob/bab84905c3871e50f3d65bebc5a8dc65eff9a1ce/src/tokens.rs)

Optional `DEDUPLICATION` guards a Mongo event token with a TTL key. This can suppress bridge retries or parallel bridge publications within that period. It cannot correlate a Meteor wrapper message with a stream event. Running both writers gives two independent messages. Even with external publishing, the method process may do local optimistic work followed by a bridge event with no UID. Re-fetch and a no-op diff often conceal duplicates from the client. Synthetic non-idempotent modifiers are a separate case. Setting `pushToRedis:false` on a wrapped write cannot suppress a separate database watcher. A bridge retry after an ambiguous Redis reply may repeat delivery. Apps must coordinate filters, prefixes, old/new namespace routing and their own downstream side-effects. [Bridge configuration](https://github.com/radekmie/changestream-to-redis/blob/bab84905c3871e50f3d65bebc5a8dc65eff9a1ce/README.md) · [Consumer dispatch](../lib/mongo/lib/dispatchers.js)

**Execution convention for the matrix.** Unit rows use pure logic or controlled promises. Integration rows use the existing server package tests with real Mongo and Redis unless explicitly marked pure. E2E adds a DDP client using the existing browser harness. “Two apps” means separate Node/Meteor processes pointed at the same disposable Mongo database and Redis instance, one performing the write and the other hosting a subscription. Bridge rows add the actual tagged executable and replica-set Mongo. Use deterministic IDs, unique collections/channels, explicit sort ties, teardown in finally, retained handles, and recorded callback sequences. Establish subscription acknowledgements with a client callback or PUBSUB NUMSUB, then use a sentinel on the same relevant stream plus the observer queue flush. | Reduce pre-reads or payloads | Single-ID vs multi 10/1,000. Previous-doc and full-image mode on/off. 1 KB/64 KB docs, narrow/broad projections. Compare read counts with bytes, allocation and stale-state checks. | Avoid a read only when affected ID and required previous image are known. No extra event for a failed/missing write, no lost update under pre-read interleave. |
| Burst processing and head-of-line blocking | Interleave a hot channel and a sparse latency-sensitive channel. Mix 1,000 event updates, repeated ID changes and synthetic increments. Compare current queue, safe grouping by independent work and bounded producer batches. | Lower sparse-channel tail latency or increased throughput with the same per-observer sequence where promised. Never coalesce non-idempotent synthetic operations or invalidate method completion fences. |
| Churn and recovery | 10,000 repeated subscribe/stop cycles, multi-channel subscriptions per cursor, reconnect with many active windows. Compare reload calls per unique query and heap after quiescence. | Measurably fewer redundant reloads, maps/NUMSUB return to baseline, surviving observers match Mongo, no extra peak memory or reconnect gap. |

### Independent Meteor upstream proposals

1. **Index exact-ID observers inside SharedChangeStream.** Each collection event currently visits every driver. Redis Oplog's direct channels suggest a per-connection map from typed ID to potentially interested drivers plus a bucket for general selectors. No Redis dependency is needed. Preserve matcher checks for extra predicates and old membership, typed-ID distinctions, unregister on stop, and preserve progress/fence advancement for skipped drivers. Benchmark many sparse ID selectors against all general selectors, measure driver calls, memory, p99 and catch-up time. Test updates, deletes, resync and stopping during dispatch. A growing reverse index may cost more than it saves at low cardinality. [Shared dispatch](https://github.com/meteor/meteor/blob/eaf134973529396b660078b705b9fa50a4747fd5/packages/mongo/shared_change_stream.js)
2. **Share type translation across drivers on the same event.** Redis Oplog loads once per channel then projects per observer. Core already shares the watch, but each driver's _handleChange converts Mongo pre/post images. Consider one read-only translated event per dispatch, retaining individual matcher/projection/diff logic. No Redis needed. Test EJSON/ObjectId/binary, callback mutation isolation, split events and snapshot/replay. Profile allocations/GC and CPU for large docs with many distinct queries versus a single driver. Full-document retention until the last consumer finishes is a potential cost. [Native conversion](https://github.com/meteor/meteor/blob/eaf134973529396b660078b705b9fa50a4747fd5/packages/mongo/changestream_observe_driver.js)
3. **Experiment with a limited sorted-window driver.** Native intentionally declines skip/limit. Eligible queries may use oplog, otherwise polling. Redis Oplog's ID-window requery and projected set diff provide a simple reference model for an opt-in change-stream strategy. Start with unordered limit, deterministic indexed sort, no skip, and conservative reconciliation on unknown updates. Compare to configured fallback under hot and idle workloads. Require correct membership on ties, inserts before the boundary, deletes, replacement, resume and resync, along with fence completion. Adopt only for workloads where the extra queries beat fallback. No Redis dependency or change to default eligibility is required for the experiment. [Window reference](../lib/processors/actions/requery.js) · [Meteor eligibility](https://github.com/meteor/meteor/blob/eaf134973529396b660078b705b9fa50a4747fd5/packages/mongo/mongo_connection.js)

Do not push an application selector into the shared Mongo watch as a shortcut. Nonmatching events can advance operation time for pending DDP fences, and a document can leave a selector or be deleted without a usable post-image. These proposals belong in Meteor with its own Tinytests and performance data.

**Rollout and rollback.** For an existing Redis 7.x server follow the standalone or cluster-specific Redis Open Source 8 upgrade guide. For an older *persistent* server stage a vendor-supported path to 7.x first, validate restore/replication at the intermediate step, and then follow the documented 7.x-to-8 path. For an exclusive, stateless Pub/Sub endpoint a fresh 8.12.0 service plus coordinated cutover avoids a data-format migration. Inventory any other keys/services, especially bridge checkpoints and dedup records, before treating the endpoint as stateless. Back up data, ACL/config and checkpoints, rehearse restore with the original binary, and record the Mongo history window. [Standalone upgrade](https://redis.io/docs/latest/operate/oss_and_stack/install/upgrade/standalone/) · [Cluster upgrade](https://redis.io/docs/latest/operate/oss_and_stack/install/upgrade/cluster/)

Canary a complete writer/reader/bridge group against the same isolated endpoint and fixture, verify startup/resubscription, projection, remote updates and latency. At cutover drain or pause production writers/bridge where practical, switch all participants coherently, verify every app's subscription and force a fresh observation/reconciliation for affected live views. Canarying a single production reader on a different broker can silently split the notification network. Monitor connection errors, ACL/script failures, message lag, resync counts and Mongo load. Roll back all endpoints as one group using the prior deployment and compatible backup, re-establish subscriptions and reconcile from Mongo. Do not rely on loading a new-format dump in an old server or replaying ephemeral notifications. Restore/stage bridge tokens only within valid Mongo history and account for replayed publications. A rollback is complete when fresh and existing subscribers agree on persisted state and a subsequent cross-instance write arrives.
